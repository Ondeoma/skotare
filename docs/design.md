# skotare の設計

## 監視の流れ

1. 監視は拠点ごとの行（`monitor_region`）を持ち、拠点ごとに `next_check_at`（次に確かめる時刻）・失敗の回数・状態を持つ。
   拠点の行は、監視の作成（今ある拠点の分）と、ノードの心拍（拠点ができたとき・起動直後・10分ごとに自分の拠点の分）で作る。
2. 各ノードの Worker は1秒ごとに、空いている数（`CHECK_CONCURRENCY` まで）だけ、自分の拠点で時刻の来た監視を取る。
   取るときに `next_check_at` を間隔だけ進める。`for update skip locked` で取り合うので、同じ監視を同じ拠点の2台が同時に取ることはない。
3. 確かめて（`core` の `Probe`）、拠点の状態を進め、監視の状態を決め直し、結果を `check_result` に残す（`MonitorStore.record`. 1トランザクション）。
   - 拠点の状態: 成功 → `up`。失敗が `retries` 回を超えて続いたら → `down`。それまでの失敗では、次の確認を20秒後に早める
   - 監視の状態: 健全な拠点（`region.health = 'ok'`）の、古くない（確かめる時刻を間隔の3倍・最低2分より過ぎていない）票を数える
     （`core` の `Judge.overall`。未確認 `pending` も1票）。停止の票が必要な数（`confirm_regions`。0 は過半数）に達したら `down`、
     正常の票が「票の数 − 必要な数」を超えたら `up`、どちらでもなければ変えない（保留. 先に確かめた1つの拠点だけで停止にしない）
   - 監視の行を先にロックする（`for no key update`）ので、拠点どうしの結果は1つずつ順に合わせる
   - 結果には、そのときの監視の判定（`up`）も残し、日ごとの集計（`check_daily`）に足す（判定に数える拠点の確認だけ. 数える拠点がなければすべて）。
     24時間の稼働率は結果から、30日の稼働率と90日の帯は日ごとの集計から、一覧の帯は確認の間隔ごとの30区間で数える
   - 停止の間は、停止と見ている拠点とその理由を、監視の最後の結果として出し続ける
   - `down` になったら障害（`incident`）を開き、`up` に戻ったら閉じる
   - 状態が変わったら（未確認 → 正常は除く）、送る通知を `notification_outbox` に入れる（通知先ごとに1行）
4. 各ノードの Worker は2秒ごとに行列から取って送る。取るときに5分先に延ばしておくので、送っている間にノードが落ちても5分後にほかのノードが送り直す。
   失敗したら1・2・4…分（最大60分）あけて、10回まで送り直す。
5. プッシュ通知・ログ・メトリクスは、状態を変えたノード（確認・拠点の判定・監視の変更）がその場で出す（`Announcer`. 受け取ると決めた端末すべてに）。

## 拠点の健全性（skotare 側の故障と、監視先の故障を分ける）

どれか1つのノードが15秒ごとに（`pg_try_advisory_xact_lock` で1台に絞る）、拠点ごとに判定する（`core` の `Judge.regions`）。

| 健全性 | 条件 | 意味 |
|---|---|---|
| `offline` | 心拍が90秒以内のノードがない | 拠点が止まっている（ノード・DB への経路の故障） |
| `suspect` | 基準点（`monitor.canary`）の過半数を、その拠点が停止と見ている | 拠点の外への出口（回線・DNS など）の故障の疑い |
| `suspect` | ほかの動いている拠点では正常な監視先の半分以上（3件以上）を、その拠点だけが停止と見ている | 同上 |
| `suspect` | ノードは動いているのに、その拠点の行がすべて確かめる時刻を大きく過ぎている | 確認が回っていない（ノードが足りない・止まりかけ） |
| `ok` | それ以外 | |

- `ok` でない拠点の票は監視の判定に数えない。健全性が変わったら、状態が変わりうる監視だけを id の順にロックして判定し直し、
  通知の行列に拠点の変化（`region.suspect`・`region.offline`・`region.ok`）を入れる（すべての監視を送る通知先にだけ）。
  `offline` になった拠点の行は未確認に戻す（戻ったときに古い票で判定しない）。
- 拠点が1つでも同じ仕組みで動く。基準点に届かなければ拠点を疑い、監視先の状態は保留する（拠点の異常だけを知らせる）。
  ただし、基準点より先に監視先の停止を判定したときは、その停止は残る（基準点は間隔を短く、監視先は `retries` を1以上にするとよい）。
- 1日以上ノードのいない拠点は片づける（拠点の行と、拠点ごとの状態を消す）。

## 冗長構成

- ノードは DB だけで協調する（ノード同士は通信しない）。ノードの数・拠点の数は自由に増減できる。
- 心拍（`node`）を30秒ごとに書き、90秒書いていないノードは止まったとみなして画面に出す。
- ログインの途中の状態（OIDC の state）・セッション・VAPID の鍵も DB にあるので、どのノードに要求が来てもよい。
- DB が単一障害点になるので、本番では PostgreSQL を冗長にする（Patroni など）。

## ステータスページ

- `status_page` と、載せる監視（`status_page_monitor`. 並びとページでの名前）。
- `GET /api/public/status/{slug}`（ログインなし. 公開しないページはログインした人だけ）は、名前・状態・90日の日ごとの稼働率・14日の障害だけを返す。
  ページに載せた監視だけを読み、ノードごとに30秒覚えておく（ページを変えたら忘れる）。
- 監視の一覧（`GET /api/monitors`）も、ノードごとに5秒覚えておく（監視を変えたら忘れる）。

## 通知の本文（Webhook）

```json
{"event": "down", "monitor": {"id": "…", "name": "会社のサイト", "kind": "http", "target": "GET https://example.com"},
 "message": "応答コード 503（期待 200-299）", "at": "2026-11-17T13:00:00Z", "downSince": null, "url": "https://skotare.example.com/monitors/…"}
```

`event` は `down`・`up`（`downSince` は停止した時刻）・`closed`（停止中に設定を変えた・一時停止したので障害を閉じた. `status` は `pending` か `paused`）・
`test`（試しに送ったとき）。

拠点の健全性が変わったときは、次の形で送る（`event` は `region.suspect`・`region.offline`・`region.ok`）。

```json
{"event": "region.suspect", "region": {"name": "osaka", "health": "suspect", "from": "ok"},
 "message": "ほかの拠点では正常な監視先 3/6 件に、この拠点だけが届きません", "at": "2026-11-18T00:00:00Z", "url": "https://skotare.example.com"}
```
